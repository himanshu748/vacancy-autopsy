# Auth0 reviewer approval

The backend can validate real Auth0 API access tokens and record a reviewer's approval of one exact report digest. That record remains **private release readiness**. An optional, separately confirmed sharing flow creates a sanitized public source snapshot; it never changes the private investigation or shares its input/evidence bodies. Sharing is disabled by default and remains disabled in the actual application. No employer is contacted, and no stale listing establishes intent.

## Configure and register

Requires direct `jose` v6 dependency. Auth0 verification uses public JWKS; it needs no client secret or Management API token. The application integration supplies these server-side settings:

```text
AUTH0_ISSUER_BASE_URL=https://YOUR-TENANT.auth0.com/
AUTH0_AUDIENCE=YOUR-CUSTOM-API-IDENTIFIER
AUTH0_CLIENT_ID=YOUR-SPA-CLIENT-ID
# Local files use DATA_DIR (default ./data); hosted mode also requires MONGODB_URI.
# PUBLIC_ORIGIN=https://your-service.onrender.com
# PUBLIC_SHARING_ENABLED=false
```

In Auth0, create/configure a custom API using RS256, enable RBAC and **Add Permissions in the Access Token**, define `review:reports`, and assign that permission only to human reviewers. The frontend must request an access token for this API audience. An ID token is not an API access token. A dedicated application/API and a genuine local product reviewer journey were verified on November 1, 2026; hosted login remains a separate gate.

On November 1, the user-approved dedicated SPA and RS256 API were configured with only `http://127.0.0.1:8787` as callback, logout and web origin. RBAC and token permissions are enabled; the SPA alone has the API's `review:reports` delegated grant, and machine access is denied. The requested Google identity first signed in without reviewer permission and received the product's denial. Only that identity then received the dedicated reviewer role. After interactive sign-in renewed its token, the actual product recorded a private, exact-digest approval for report `c7083b27-7924-4813-8050-54d20e5a1dcd`. A separate Atlas connection validated the saved approval and its report digest. No access token, raw subject, email or client secret was retained in the evidence receipt. See workspace `outputs/evidence/auth0-live-receipt.json` and the product screenshot `auth0-live-approved.png`, outside the source ZIP.

Google social login currently uses Auth0 development keys, with the default basic/extended profile scopes. Silent renewal required interactive consent in this browser. Production social credentials, hosted callbacks and federated logout remain unverified. Public sharing stays off, and this private approval did not publish a finding. Earlier administrative quota observations no longer block this new dedicated setup. No unrelated application or billing setting was changed.

The application entry point configures the verifier and registers approval routes automatically. Set these values in the project environment; no custom route registration or client secret is needed. With `MONGODB_URI`, approvals use the same database as workspace artifacts; otherwise local approvals live in `DATA_DIR/approvals`.

The default local desk retains its localhost bind, Host/Origin guard and rate limit. Optional hosted mode is a **single private workspace**: every authorized human with `review:reports` can access that workspace's private reports. It is not a multi-tenant isolation model and does not authorize deployment. The server enforces a default-deny JWT boundary before every protected route. GET/HEAD requests for the root shell, known assets/fonts, health and reviewer configuration are public. One exact 64-hex shared-report path permits anonymous reads, but returns 404 while sharing is off or the release is absent/withdrawn. It has a separate 60/minute address budget and no anonymous listing. Investigation history, evidence downloads, source tools, rechecks, previews, approvals, publication and withdrawal require a verified permitted human. Authenticated request budgets use the issuer-bound subject hash; public shell/health traffic does not consume that budget. Failed authorization has its own bounded IP bucket. No unrestricted proxy-header trust is enabled.

## Reviewer interface

`src/web/ReviewerPanel.tsx` exports `ReviewerPanel({ report })` (also the default export). Shared `workspace-auth.ts` reads `GET /api/reviewer-config`, which includes `requiresAuthentication` and `sharingEnabled` booleans alongside `configured` and, when configured, `issuer`, `clientId` and `audience`. These are public application settings, not secrets. A missing or malformed authentication-mode field fails closed; missing sharing metadata defaults off. Missing local reviewer configuration produces an explicit disabled sign-in state and never calls Auth0.

The application wraps its desk in `WorkspaceGate({ children })` and mounts the reviewer panel for the selected report. The gate processes OAuth callbacks before reports mount, shares a single SDK client with the reviewer panel, and in hosted mode validates access through protected `GET /api/workspace` before showing the desk. The expected response is `{ authorized: true, visibility: "private_workspace" }`; a public health response is not authorization evidence. A 401/403 from protected fetches closes the hosted gate, with explicit sign-in or role-permission feedback. Local mode passes through after configuration is read.

The desk reads the exported `getReviewerReturnReportId()` during initial app loading and restores that report through its investigation endpoint. The helper reads only a validated report UUID from session storage. Callback processing leaves it available until the restored reviewer panel mounts, preventing a callback/restoration race. The panel then clears it; sign-out also clears it. Report bodies, access tokens and user profiles are never written to application storage.

Replace direct frontend API fetches with `authorizedFetch(path, options)`. It accepts only same-origin `/api/` paths, forces same-origin credentials and redirect refusal, and adds an in-memory bearer when hosted authentication is required. `reviewerFetch` adds the reviewer token even in local mode. Tokens are never put in URLs. Direct download anchors cannot send bearer headers: their click handler calls `authenticatedDownload(event, path).catch(showError)`. Local links retain their native behavior; hosted JSON is fetched with authorization and downloaded verbatim through a short-lived blob URL. The helper refuses external targets and non-JSON responses. This includes investigation, search-provenance and browser-evidence downloads.

Configure an Auth0 **Single Page Application** with the current local app origin in Allowed Web Origins, and its root URL (for example `http://127.0.0.1:8787/`) in Allowed Callback URLs. The frontend client ID is `AUTH0_CLIENT_ID`; it must belong to that application. Set its allowed logout URL if using a full Auth0 logout elsewhere. This panel clears only the local review session without federated logout.

The shared SDK client implements PKCE and uses `createAuth0Client`, `handleRedirectCallback` and `getTokenSilently`, requesting only `openid review:reports`. Tokens stay in its memory cache, with refresh tokens disabled. The SDK may retain its own short-lived OAuth transaction material for PKCE; no access or refresh tokens are put in local/session storage. The callback always returns to this origin's root, ignores arbitrary `appState` navigation, and removes authorization parameters from browser history after processing. Permission errors never become successful approvals. The interface compares the complete returned review report with the currently visible report before enabling the acknowledgement and submit action.

When reviewer access is configured, the server's Content Security Policy must permit **only the validated issuer origin** in `connect-src` (token requests) and `frame-src` (silent sign-in). Keep other external origins blocked. The bundled SDK needs no external script/CDN allowance. Browser privacy settings can prevent silent sign-in; the UI then asks for interactive sign-in again instead of persisting tokens.

The actual in-app browser has exercised configured PKCE redirects, Google login, missing-permission denial, role assignment, renewed authorization and a private approval. Earlier responsive and keyboard checks covered the unconfigured interface. Hosted bearer-download behavior remains contract-tested, not a hosted browser receipt.

## Review protocol

1. An authenticated reviewer calls `GET /api/investigations/:id/review` with an `Authorization: Bearer …` header. It returns the full private report, `reportDigest`, `digestAlgorithm`, and that reviewer's approval for the current digest, if one exists.
2. The interface presents the actual evidence and limitations, then obtains an explicit confirmation. It posts to `POST /api/investigations/:id/approvals` with exactly `{ "reportDigest": "<digest from review>", "confirmation": "I reviewed the evidence and limitations" }`.
3. The server re-reads the immutable report and recomputes its digest. A mismatch returns 409 and records nothing. Illustrative reports or reports with no captured evidence cannot be approved.
4. A matching approval is stored atomically and returned with `publication: "private"`. Retrying the same report/reviewer pair returns the original record and approval timestamp. A changed report does not inherit the old approval.

The digest covers the validated full report, including ID, evidence body, verdict, limitations, source timestamps and input, using recursively sorted object keys, preserved array order, and a versioned SHA-256 domain prefix. Clients use the server-provided digest rather than duplicating canonicalization. Future schema/policy changes need a new digest/policy version.

JWT verification pins RS256 and the configured issuer/audience; requires expiry, issue time and subject; validates not-before and caps token age at 24 hours with five seconds of clock tolerance. Only the configured issuer's JWKS is used; token-supplied key URLs cannot choose the verifier. JWKS retrieval has a five-second timeout, ten-minute cache, and thirty-second refresh cooldown. Permission must appear in the Auth0 RBAC `permissions` array; a bare `scope` claim does not substitute. Client-credentials grants and `@clients` machine subjects are denied. These checks enforce the assigned identity/permission; they cannot prove a person read the evidence or prevent a compromised authorized account from confirming it.

Approval records contain the report ID/digest, approval time, policy/permission and an issuer-bound subject hash. Tokens, raw subject IDs, emails, profile data and duplicate evidence bodies are not persisted. The local store uses private 0600 files, atomic exclusive writes and a 1,000-record cap. It is single-process development storage. The MongoDB approval adapter validates immutable records, unique IDs and acknowledged writes. The real Atlas workspace store now preserves reports and source artifacts across API/worker restarts, and required indexes on the approval collection were verified. A real Auth0-authorized approval was written through the product and read through a new Atlas connection, with its immutable record and report digest validated. Approval revocation and multi-tenant ownership remain unimplemented.

## Optional reviewed sharing

Enable `PUBLIC_SHARING_ENABLED=true` only after explicit authorization and complete Auth0 setup. This does not authorize deployment or publishing any particular case. The actual application configuration remains off. An approved private report exposes **Preview a share link** only when the server advertises sharing enabled.

1. `GET /api/investigations/:id/share-preview` requires a permitted human token. The server validates source/evidence freshness within 24 hours (five-minute clock tolerance), verifies all saved official-feed SHA-256 hashes and replays the deterministic ATS verifier against captured bytes with a network-free exact-URL transport. The public title comes from those official bytes, not pasted advertisement text or free-form report copy. An unverifiable observation returns 409. A stale observation cannot create a new share; an already-existing historical release can still return its validated preview with `publishable: false`, preserving the reviewer's ability to withdraw it after the publication window expires.
2. The preview contains a canonical supported ATS identity, source-only verdict, check time, fixed qualified statement/limitations, and source URLs/times/hashes. A third-party advertisement's source observation can be shared only as a finding about the supplied ATS opening; the preview expressly does not establish advertisement linkage or company-domain ownership. No raw input, evidence body, reviewer identity, approval record or private report digest appears in the public snapshot.
3. After reviewing the exact displayed projection, the human explicitly confirms **making it readable to anyone with the link**. `POST /api/investigations/:id/share` requires the current `reportDigest`, exact `previewDigest`, and confirmation `Publish this exact reviewed source finding`. The server independently replays/validates the report, requires this same human's matching current private approval, checks the report again, and atomically records the release. A changed report/preview, missing/stale approval, machine token or integrity failure cannot release it.
4. `GET /api/shared-reports/:id` serves only the validated public snapshot. Its `/?shared=<id>` page opens directly without a workspace login and shows the original check timestamp and qualifications. Source investigations retain `publication: private`. There is no public history/list/search endpoint. Private source/preview/approval digests and reviewer hashes stay only in the private release record.
5. `POST /api/shared-reports/:id/withdraw` requires a permitted human token and confirmation `Withdraw this shared finding`. An append-only tombstone stops subsequent reads with 404; it preserves the private report and approval. A retry of publication cannot reactivate the withdrawn ID. Recheck the opening to create a new report/share. Withdrawal cannot recall copies already downloaded by recipients.

Local releases use private atomic files under `DATA_DIR/shared-findings`, with a 1,000-release cap. With MongoDB, an additional bounded connection creates unique-ID collections `shared_findings` and `withdrawn_findings`; writes require acknowledgement and reads validate records/digests. Both adapters preserve tombstones across instances/restarts. Every public read re-reads release/withdrawal state and uses `Cache-Control: no-store`. A database failure returns an unavailable response, never a private-report fallback. An unconfirmed write may nevertheless have persisted: reload the preview to reconcile its status before retrying.

These are local implementation and synthetic authorization proofs. The public page and withdrawal were browser-checked with clearly labeled synthetic evidence at desktop and narrow widths. A separate real Atlas adapter-only smoke wrote, read, retried, reconnected and irreversibly withdrew one synthetic record; unique indexes and withdrawal preservation passed. It used no public server route or real approval, and the actual app's sharing setting remained off. The receipt is outside the source ZIP at workspace `outputs/evidence/atlas-release-store-smoke-receipt.json`. Local Auth0 reviewer login and private approval are now verified; a user-authorized real report publication and hosted serving remain separate acceptance gates. No real finding has been released by these tests.

Tests use generated RS256 keys, a real local JWKS resolver and the actual Fastify entry point with synthetic reports. They check valid signatures, wrong issuer/audience, missing/expired/future claims, forged/unknown keys, algorithm substitution, missing permission, machine identities, report mutations, private immutable storage, idempotent retries and credential-safe errors. Sharing tests additionally exercise exact sanitized previews, integrity/freshness failures, acknowledged/uncertain writes, anonymous route budgets, restart persistence and irreversible withdrawal. Hosted-access tests exercise the actual default-deny route gate, separate public/authenticated budgets and independent human reviewer budgets. This proves local enforcement, not an Auth0 tenant login or sponsor qualification. The temporary local tests create generated test credentials and synthetic snapshots, but no provider credential, cloud account, payment, deployment or real public finding.

The workspace transport contract test uses a synthetic browser/config fixture and restores its global fetch/window after execution. It verifies local pass-through, same-origin API confinement before SDK initialization, redirect refusal, native local downloads, case-ID restoration, malformed configuration refusal and hosted misconfiguration refusal. It makes no provider call and does not prove a configured Auth0 browser login or hosted bearer-download receipt.
