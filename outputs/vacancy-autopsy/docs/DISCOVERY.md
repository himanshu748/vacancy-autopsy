# Discovery and restricted browser capture

These optional adapters support finding and retaining public source leads. They do not predict employer intent or submit applications. Provider-contract tests use synthetic responses. SerpApi is connected under explicit user authorization and its first two successful searches completed through the browser app following a malformed-URL validation repair. Both searches returned advertisement leads; exact first-party-counterpart discovery remains unverified. Browserbase captured a real OppIDX advertisement through the app on November 1, 2026, retained hash-verified DOM/PNG evidence and separately confirmed its fresh session completed. The capture contained the Figma posting link; this does not prove historical removal or employer intent.

## Server integration

The server passes configuration privately and invokes a provider only after the user requests that operation through the source-tools interface. No API key belongs in browser JavaScript or request bodies from the frontend. Configuring a key is not a billing authorization or a successful integration receipt.

```ts
import { discoverJobs, discoveryInputSchema } from './discovery.js';
import { captureAdvertisement, captureInputSchema } from './browser-capture.js';

const query = discoveryInputSchema.parse(request.body); // { query: string }
const leads = await discoverJobs(query, { apiKey: process.env.SERPAPI_API_KEY, signal });

const target = captureInputSchema.parse(request.body); // { url: public HTTPS URL }
const capture = await captureAdvertisement(target, {
  apiKey: process.env.BROWSERBASE_API_KEY,
  projectId: process.env.BROWSERBASE_PROJECT_ID,
  signal,
});
```

The integrated routes use the server's Host/Origin controls, operation rate limit and request cancellation. `POST /api/discovery` and `POST /api/captures` persist immutable private artifacts; `GET /api/research/:id/report` downloads them. The local desk is loopback-only, while hosted mode requires the workspace bearer for all three endpoints. One source-tool operation may run at a time in this process. Invalid input raises a Zod validation error. Missing configuration returns `not_configured` with no provider call. Provider failures return a safe `failed`/`cancelled` result without raw exception strings or connection URLs. The routes persist independent discovery/capture artifacts; the helpers themselves do not mutate investigation records.

Discovery returns candidate URL, title, snippet, position and candidate type. `provenance` holds the provider search ID when available, one-request count, the exact normalized result projection and its SHA-256. It deliberately does not store raw provider metadata or a request URL carrying `api_key`. A projection hash authenticates the retained projection, not the underlying page or a complete raw search response. An ATS URL is labeled `official_posting_candidate`; it has not yet been checked.

Capture returns a timestamped `browser_capture` evidence record containing the exact retained JSON DOM observation and its hash. A separate optional PNG artifact has base64 bytes, byte count and a byte hash. Persist image bytes with private access and display the stated capture restrictions alongside them. `officialLinks` contains exact supported ATS URLs observed in the first 80 anchors. A page linking to an opening is useful evidence, but does not independently establish employer ownership, title equivalence or current availability. Selecting a captured link explicitly may attach it to a new investigation under the validation contract below; a capture alone never changes a report.

## Attach a saved advertisement snapshot

After capture, **Use this captured posting link** fills the source and ATS URLs and attaches its private artifact reference. The user then submits the normal investigation. The same shared pure identity parser deduplicates Greenhouse legacy hosts, Lever `/apply` links and Ashby `/application` links in the UI and server; these equivalent aliases stay unchanged in the hashed source projection. Editing either URL or choosing a model/search/shortlist suggestion clears the attachment. An attached snapshot is visible and removable; there is no silent attachment or publication.

`POST /api/investigations` accepts optional `captureArtifactId` (UUID). It accepts no client-supplied evidence body or linkage flag. API preflight and the investigation's execution process load the saved artifact from the configured private artifact store. The existing artifact validator verifies DOM and optional PNG hashes; attachment additionally requires:

- A successful restricted Browserbase capture with a retained DOM body, matching capture timestamps and an artifact created no earlier than that capture.
- Capture age at most 24 hours, no more than five minutes in the future, and artifact creation within five minutes of capture. These are observation freshness bounds, not a claim the page remains unchanged.
- The requested, final and evidence source URLs all match the sanitized advertisement URL on a supported fixed host; redirects to another page cannot establish this attachment.
- The hashed DOM projection's `officialLinks` exactly matches the stored result metadata. Its links must resolve to one unique supported ATS posting identity, matching the supplied official URL. Different canonical aliases of the same identity are allowed; multiple job identities are rejected.

Missing, stale, corrupt, blocked, inconsistent or mismatched captures never cause a feed fetch or a supported advertisement verdict. Readable artifacts that fail attachment checks return a controlled error asking for a new capture. Storage read/parse failures remain unavailable rather than being interpreted as missing evidence. Without an attachment, the previous behavior is preserved: a supplied official URL can produce a separate source observation, while an unverified third-party advertisement stays inconclusive.

A successful attached check retains the browser DOM evidence and its hash alongside the independently fetched official source. It states that the captured page contained a link to that exact posting; it does not establish title equivalence, employer domain ownership, hiring intent, successful applications or prior removal. The screenshot stays in its downloadable private artifact rather than being duplicated into every report.

Temporal input contains only the artifact reference plus normal investigation input. The Activity opens its own bounded private artifact-store connection and validates the capture there; DOM/PNG bytes never enter Temporal workflow input or Activity results. A retry after persistence reuses the exact immutable report without rereading expired capture evidence or refetching the source. A user recheck creates a new report and validates freshness again; after 24 hours the user must capture again. Old reports and approval digests remain unchanged.

To keep an expired case's history linked, open it, recapture its advertisement, select the captured link and choose **Recheck with refreshed snapshot**. That action appears only when the new selection matches the saved source URL and ATS identity. `POST /api/investigations/:id/recheck` accepts only an optional `{ "captureArtifactId": "fresh-artifact-uuid" }` body; URL, posting identity and other original input are pinned to the saved report. The server independently validates the replacement and creates a new report with `previousInvestigationId`; a fresh capture from a different advertisement or job is rejected. Plain **Recheck source** retains the previous reference and its freshness rules.

## Bounds and access behavior

SerpApi uses one synchronous first-page Google search, a ten-second request deadline, no retry or pagination, a 1 MB response cap and at most ten retained unique candidates. It inspects the first 100 organic rows and the first 100 sitelink rows globally, including malformed rows in those budgets. Only the documented `sitelinks.inline`, `sitelinks.expanded` and `sitelinks.list` arrays are inspected, in that order within each organic row; arbitrary nested metadata, redirect URLs and Google Jobs blocks are not traversed. A missing or malformed parent URL does not discard its valid sitelinks, and invalid siblings are skipped independently.

Candidates are normalized and deduplicated before retaining up to ten. Exact supported ATS posting candidates precede other leads, with provider order preserved inside both groups, so board roots do not crowd out a nested exact posting. `position` records the parent organic rank rather than the final displayed order. A sitelink uses its own title and snippet, never the parent board's text as a substituted job description. This ordering and source label do not establish ownership, correspondence to an advertisement or availability. Cached results are allowed and explicitly qualified. Snippets can be old; the verifier must still fetch the first-party source. Result URL queries and fragments are removed before storage.

Browserbase creates at most one concurrent session in this process. A session requests a 60-second provider timeout, `keepAlive: false`, no proxy, no CAPTCHA solving, no stealth, and normal certificate validation. There is no context, cookie or login reuse. The local operation has a 35-second budget plus an independent eight-second cleanup request. Creation is never retried: a timed-out creation might have created an unknown session, which should expire at its requested provider timeout. A duration bound is not a guaranteed dollar cost or a grant of free usage.

Capture destinations are fixed exact hosts: OppIDX, Employbl and the supported Greenhouse, Lever and Ashby posting hosts. Arbitrary employer domains are unsupported. DNS answers must all be public global addresses. The provider's `allowedDomains` setting restricts main-frame navigation **only**, including subdomains; it is not a resource egress firewall. Therefore capture also disables page JavaScript before navigation, bypasses service workers and intercepts every CDP Fetch request. The handler permits only GET/HTTPS requests to a fixed exact host set after public-DNS validation; it blocks redirects, frames and resources outside that set, credentials, custom ports, and private/reserved addresses. Eighty requests are the maximum allowed. Failures in interception terminate capture.

The adapter explicitly creates in `us-west-2` and constructs the documented `wss://connect.browserbase.com/` connection with exactly two encoded query parameters: the configured API key and the validated ID from that fresh REST response. It never opens the response's `connectUrl`, whose current opaque signing-key form does not promise a visible `sessionId`. Thus a returned foreign endpoint, duplicate/ambiguous ID or signed URL cannot redirect the connection into an existing session. The key-bearing URL stays in memory and is excluded from results, logs and evidence. Only that same newly created ID is released; no session list/history lookup is made. This endpoint construction follows Browserbase's current [REST-create/CDP-connect integration example](https://docs.browserbase.com/integrations/braintrust/typescript); synthetic tests do not establish live transport compatibility.

Local DNS checks cannot pin how a remote provider resolves a hostname. The fixed trusted-host restriction is intentional; do not replace it with an arbitrary user-controlled hostname allowlist. Page JavaScript remains disabled to prevent page WebSocket/worker/pop-up traffic outside Fetch interception. No dynamic application-state claim is supported. Access-denied/CAPTCHA pages are retained as `blocked`; no bypass is attempted.

The snapshot is limited to 16,000 text characters, 80 anchors and a 1280×900 viewport screenshot below 1 MB. Other resource requests may be blocked, so appearance/content can be incomplete. Hashes refer to that declared subset. This is useful static-browser evidence, not a complete page archive or proof a form accepts submissions.

Known sessions receive an explicit release request in `finally`, even after cancellation or unsafe transport data. Cleanup has its own uncancelled deadline. The response must identify the same session with a terminal state before `cleanup: released` is returned. A successful HTTP response reporting a still-running session remains `cleanup: release_failed`, meaning release could not be confirmed. The provider's hard timeout remains the final bound.

## Verification and remaining gates

Run `npx tsx --test --test-concurrency=2 tests/capture-linkage.test.ts tests/discovery-capture.test.ts tests/discovery-sitelinks.test.ts tests/research-routes.test.ts tests/mongo-workspace.test.ts tests/temporal-activities.test.ts`. Tests exercise bounded discovery, all three documented sitelink shapes, malformed siblings and parents, stable exact-ATS-first selection, retained hashes, missing configuration, malformed/oversized/invalid-UTF-8 provider responses, private/reserved DNS, canonical fresh-session CDP binding despite hostile or opaque returned URLs, credential-query injection, invalid session IDs, final redirects, request interception, main-frame status handling, blocked access, cancellation and cleanup. Attachment tests cover source/identity/hash/metadata mismatch, stale/future timestamps, multiple identities, untrusted client fields, durable preflight, reference-only Activity boundaries, retry reuse, immutable downloads and rechecks. All responses and the CDP connection in these tests are synthetic fixtures; the separately retained actual run establishes live capture transport. The sitelink coverage change has no live exact-counterpart receipt by itself.

The source-tools interface was first exercised in the in-app browser without credentials: search and capture returned explicit unavailable states. Later, the user approved connecting the existing SerpApi account key. The first real browser search failed safely; an account-API check established active access, and a bounded diagnostic of the same cached query returned HTTP 200, provider status Success and nine organic results. A malformed lead could throw from shared URL refinement despite `safeParse`, losing the whole result. The shared validator now rejects malformed URLs without throwing, and discovery skips invalid candidates. API-400 and mixed-validity regressions cover the repair. Sentry retained the initial failed operation and its latency.

After the repair, a browser search for “Figma Brand Design Intern Summer 2027 Greenhouse” saved discovery artifact `ab8c2bbd-4990-4a79-a4b6-c1af0f747e82` with two real advertisement candidates. Its JSON download succeeded and the retained projection's SHA-256 matched. A second browser search for “site:jobs.ashbyhq.com/semgrep Software Engineer Intern” returned one ZipRecruiter advertisement lead. Neither search returned an exact supported first-party posting candidate, so the counterpart-discovery gate is still open. The local receipt is workspace `outputs/evidence/serpapi-live-discovery.json`, outside the shareable source ZIP. These are discovery leads, not captures or availability findings. Both retained source artifacts were subsequently migrated to the real Atlas store with matching hashes; application reports were also restored after API/worker restart. This persistence check does not satisfy the missing official-counterpart or Browserbase capture gates.

A separate initial OppIDX observation used the user's browser and did not satisfy the Browserbase gate. With no available Free project slot, the user explicitly approved storing the existing Personal project key only in this project's ignored configuration for fresh Vacancy Autopsy sessions using included minutes. Existing sessions, the key and billing settings remain unchanged. One controlled diagnostic created a new session (HTTP 201), rejected its opaque transport under the former query-only binding check, released it (HTTP 200), and separately confirmed it completed. No DOM or screenshot was produced by that diagnostic. After the canonical transport repair, a real app capture on November 1 retained the OppIDX advertisement text, its exact Figma ATS link and a 100,483-byte PNG. Both hashes matched, cleanup reported released, and a read of only that newly created session confirmed COMPLETED. Receipts are outside the source ZIP at workspace `outputs/evidence/browserbase-live-receipt.json` and `browserbase-live-session-status.json`. A subsequent actual browser journey explicitly attached a fresh OppIDX capture and ran the Temporal investigation; its new private report retained both browser and official evidence and found the exact ID absent from a complete 140-posting feed. This establishes the connected capture/check path at that timestamp, not historical removal. Refreshed-snapshot replacement and canonical-alias selection additionally have synthetic regression tests; their browser checks remain separate.

Before a sponsor claim, retain a successful live discovery projection and a real capture screenshot/DOM artifact with source URLs and timestamps, plus provider session/release receipts. Check actual account quota and allowed features before enabling calls. The adapters do not establish free-plan availability, actual credits, sponsor eligibility, historical stale-ad labels or a successful public deployment.
